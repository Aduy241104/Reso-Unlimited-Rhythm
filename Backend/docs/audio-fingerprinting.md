# Audio fingerprinting and copyright matching

Reso stores two different hashes:

- `sourceAudioHash` is SHA-256 of the original audio bytes. It detects an exact byte-for-byte duplicate.
- Chromaprint is a sequence of audio-content frames generated by `fpcalc`. It is used for re-encoded, trimmed, or offset audio.
- Evidence SHA-256 belongs to copyright documents and is not an audio fingerprint.

## Local engine

The backend resolves `fpcalc` in this order:

1. `FPCALC_PATH` when explicitly configured.
2. The project-relative binary at `Backend/tools/chromaprint/fpcalc` (or `fpcalc.exe` on Windows).

The repository does not contain a machine-specific binary. `npm install` runs `scripts/setupChromaprint.js`, detects `process.platform` and `process.arch`, downloads the matching official Chromaprint 1.6.1 `fpcalc` package into `Backend/tools/chromaprint/`, and verifies it with `fpcalc -version`. A valid local binary is reused on later installs. The downloaded directory is ignored by Git and is intentionally not committed or redistributed by this repository.

`FPCALC_PATH` remains available as an optional override for CI, containers, or a system-managed installation. It should normally be left empty for local development. If setup fails, `npm install` exits with an actionable error instead of silently disabling fingerprint moderation.

Check the installation before starting the backend:

```powershell
# Windows PowerShell (bundled binary)
& ".\tools\chromaprint\fpcalc.exe" -version

# Optional override
& "$env:FPCALC_PATH" -version
```

```bash
# Linux/macOS (bundled binary)
./tools/chromaprint/fpcalc -version

# Optional override
"$FPCALC_PATH" -version
```

The installer uses the official packages listed by [AcoustID's Chromaprint download page](https://acoustid.org/chromaprint). Chromaprint is licensed under LGPL-2.1. Because this project downloads the upstream package at install time and ignores `Backend/tools/chromaprint/`, it does not commit or redistribute the binary. Keep the upstream notices if you redistribute a separately built deployment image.

## Processing flow

Track creation stores a pending `AudioFingerprint` record. A lightweight background job downloads only backend-approved Cloudinary audio URLs, computes SHA-256, runs `fpcalc -raw -json`, stores the raw fingerprint internally, updates `CopyrightRegistry`, and compares bounded duration candidates.

The comparison uses unsigned 32-bit frame Hamming similarity, a bounded offset alignment window, duration compatibility, and overlap ratio. Exact source-byte hashes are checked first; candidates for Chromaprint comparison are bounded by duration and exclude exact-hash candidates. A match creates an internal `AudioFingerprintMatch` and a rule-based risk signal. Automatic moderation may reject exact/high-confidence duplicates; a clean screen remains pending for Admin review and does not provide legal proof of copyright ownership.

`CopyrightRegistry` keeps the relationship between a Track, the recording metadata (`recordingId`, title, owner, ISRC), the musical-work metadata (ISWC/composer/lyricist), and verification history. ISRC/ISWC/PRO fields are declarations or manual-review inputs; they are not treated as proof without an admin decision. After a completed fingerprint, the backend performs a cached and rate-limited MusicBrainz metadata lookup and stores the artist declaration beside the normalized external result. `matched`, `possible_match`, `not_found`, and `failed` results are all review references; MusicBrainz never auto-rejects a track.

## Operations

```text
POST /api/admin/tracks/:trackId/fingerprint/reprocess
GET  /api/admin/tracks/fingerprint-matches
GET  /api/admin/tracks/fingerprint-matches/:matchId
POST /api/admin/tracks/fingerprint-matches/:matchId/review
GET  /api/admin/tracks/fingerprint-metrics
```

Use the backfill scripts in dry-run mode first:

```text
node scripts/backfillAudioFingerprints.js --batch-size=20
node scripts/backfillAudioFingerprints.js --apply --retry-failed --batch-size=20
node scripts/rebuildFingerprintMatches.js --apply --batch-size=100
```

Fingerprint matches are signals for admin review or automatic moderation. Exact SHA-256 duplicates and high-confidence Chromaprint matches can be rejected automatically. A clean result is only `screening passed`: it does not approve the track and does not prove legal ownership. The Admin approval gate still requires the review session checklist, including audio review, copyright declaration review, fingerprint acknowledgement, and every required evidence document.

`FINGERPRINT_AUTO_APPROVE` is retained for old deployments but is intentionally ignored by the current moderation service so a clean screen cannot bypass human copyright review. Fingerprint failures leave the track pending and block approval until the screen succeeds.

Soft-deleted tracks keep their fingerprint and audit history, but are excluded from blocking a new upload or from new automatic match creation. Non-deleted tracks remain eligible for matching so active copyright conflicts can still be detected. Physical purge is outside this fingerprint job.

## Track deletion lifecycle

The artist delete endpoint is a soft delete. Before deleting storage, it records the lifecycle decision:

- An unsubmitted draft performs operational cleanup of `AudioFingerprint`, `AudioFingerprintMatch`, and `CopyrightRegistry`. Active moderation review sessions are marked abandoned.
- A rejected copyright/duplicate/policy violation is moved out of the active matching scope and copied to `CopyrightFingerprintBlocklist`. Its source/variant audio is kept for investigation, while the retained hash/fingerprint record contains no additional audio copy.
- An approved or otherwise reviewed track keeps historical fingerprint, registry, and match data for audit, but those records are not active duplicate candidates.

The active matcher requires both an active fingerprint scope and a non-deleted Track. Retained enforcement evidence is queried separately, so it can still block an exact re-upload even after the original Track is no longer visible. The current Track ID is excluded from all candidate queries, and match records carry audio versions so an updated audio file cannot reuse a stale self/match result.

`npm run fingerprint:lifecycle` is a dry-run maintenance report. It counts missing-Track fingerprints, deleted-draft hashes, stale processing jobs, orphan matches, retained enforcement evidence, and unowned Cloudinary audio variants. Only `--apply` performs cleanup; retained enforcement evidence is never removed by this script. Legacy deleted violation fingerprints can be migrated into the blocklist by running the same script with `--apply`.

For databases created before the soft-delete index was introduced, repair the stale Track title/version index once:

```powershell
npm run migrate:track-indexes
npm run migrate:track-indexes -- --apply
```

The first command is read-only and reports active duplicates. The apply command refuses to proceed when such duplicates exist, makes legacy documents' missing `isDeleted` state explicit, drops the old unconditional unique index, and keeps the unique index scoped to `isDeleted: false`.
